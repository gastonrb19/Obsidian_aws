### Descripción del servicio
Load balances are servers that forward traffic to multiple servers (e.g ec2 instances ) downstream

#### Why use a load balancer
- Spread load across multiple downstream instances
- Expose a single point of access (dns) to your app
- seamlessly handle failures of downstream instances
- do regular health checks to your instances
- provide ssl termination (HTTPS) for your websites
- Enforce stickiness with cookies
- high availability across zones
- Separate public traffic from private traffic.
- AWS guarantees that it will be working
- Aws take care of updates, maintenance, high availability
- Aws provides only a few configurations knobs (buttons)
- Good integration with several of the services available in AWS.
### Sticky sessions
Is the practice to send the traffic toward a specific instance or service (ec2, lambda, ecs) with a cookie. This could be helpful when you wants to keep the data of the session in an instance. 
##### Cookies inside of the sticky session
- Application-based cookies
	- Custom cookie
		- Generated by the target
		- Can include any custom attributes required by the app
		- cookie name must be specified individually for each target group
		- **Don't use AWSALB, AWSALBAPP, or AWSALBTG is reserver by the ELB**
	- Application cookie
		- Generated by the load balancer
		- Cookie name is AWSALBAPP
	- Duration-based cookies
		- Cookie generated by the load balancer
		- cookie name is AWSALB for ALB, AWSELB for CLB
### Health checks
This is done by a protocol, a port and also by a route. 
It will check if the response is 200, then if the instance response with success the EC2, lambda or any other service will receive the request. In case that is negative it going to delegate the traffic to other instance or service.
### Types of load balancers
Aws has 4 kinds of managed load balancers:
- Classic load balancer ( v 1 - old generation) - 2009 - CLB (DEPRECATED)
	- Support Http, Https, Tcp, Ssl (secure tcp)
- Application load balancer (v 2 - new generation ) - 2016 - ALB
	- Http, https, websocket
- Network load balancer ( v 2 - new generation ) - 2017 - NLB
	- TCP, TLS (Secure TCP), UDP
- Gateway load balancer - 2020 - GWLB
	- Operates at layer 3 (network layer) - IP protocol
	
**Overall it is recommended to use the new generation of load balancer**
- Some load balancers can be setup as internal (private ) or external (public) ELBs

### Application Load Balancer (v2)
- App load balancer works in layer 7 (http)
- Load balancing to multiple http apps across machines (target groups)
- Load balancing to multiple apps on the same machine (eg: containers)
- Support for http/2 and websocket
- support redirects (from http to https for example)
- ALB are a great fit for micro services & container app
- Has a port mapping feature to redirect to a dynamic port in ECS
- In comparasion, we'd need multiple classic load balancer per application
Routing tables to different target groups by:
- Based on path in URL ("example.com/**<path_to_track>**")
- Based on hostname in URL ("one.example.com & eee.com")
- Based on query string, headers ("example.com/users?jamoncito")
Target groups:
- EC2 instances (can be managed by an auto scaling group) - HTTP
- ECS Tasks (managed by ECS itself) - HTTP
- Lambda functions - HTTP request is translated into a JSON event
- Ip addresses - must be private IPs
- ALB can route to multiple target groups
- Health checks are at the target group level
**Relevant information**:
- Fixed hostname (XXX.region.elb.amazonaws.com)
- The aplication servers don't see the IP of the client directly
- To get the client information we must try to access via the following:
	- The true IP of the client is inserted in the header X-Forwaded-For
	- We can also get Port (X-Forwaded-Port) and proto (X-Forwarded-Proto)
